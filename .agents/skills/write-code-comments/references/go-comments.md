оформление, а не готовую реализацию.

## Назначение и контракт API

Doc comment начинается с имени объявления и кратко объясняет, что операция
даёт вызывающему коду. Не пересказывай сигнатуру.

Для простых методов достаточно одной строки:

```go
// Name возвращает имя пользователя в формате <first> <last>.
func (u User) Name() string {
    return u.FirstName + " " + u.LastName
}
```

В примере выше полезна вторая часть в виде формата <first> <last>. 
Без неё комментарий сводился бы к пересказу имени.

Не добавляй сюда рассуждения о хранении в БД или валидации: форматирование
строки таких свойств не обеспечивает.

Если результат можно изменять и это важно для вызывающего кода, объясни
последствие:

```go
// Get возвращает копию конфигурации для id. Изменение результата не затрагивает
// внутреннее хранилище. Если конфигурации нет, возвращает nil и false.
func (c *Store) Get(id string) ([]byte, bool) {
    data, ok := c.items[id]
    return bytes.Clone(data), ok
}
```

```go
// Плохо: пересказ сигнатуры.
// NewStore создаёт хранилище на основе пула соединений pool.
func NewStore(pool *Pool) *Store

// Хорошо: либо без doc comment, либо с контрактом, которого в сигнатуре нет.
// NewStore использует pool, но не владеет им: закрывать соединения должен вызывающий.
func NewStore(pool *Pool) *Store
```

## Когда комментарий не нужен

Не документируй структуру, если её поля говорят сами за себя:

```go
// Плохо: пересказ полей и тегов.
// user описывает запись пользователя, где id задаёт уникальный номер,
// name содержит имя, а age — возраст, начиная с 18 лет.
type user struct {
    ID   int    `json:"id"   validate:"gte=1"`
    Name string `json:"name" validate:"required"`
    Age  int    `json:"age"  validate:"gte=18"`
}

// Хорошо: структура без общего комментария. Пояснение только у поля,
// где есть неочевидная причина выбора типа.
type user struct {
    ID   int    `json:"id"   validate:"gte=1"`
    Name string `json:"name" validate:"required"`
    Age  int    `json:"age"  validate:"gte=18"`
    // Meta хранит произвольный JSON: его структура зависит от клиента.
    Meta json.RawMessage `json:"meta"`
}
```

Не комментируй очевидные проверки внутри функции, если смысл уже передан
в doc comment или ясен из условия:

```go
// Не нужно: doc comment Load уже сказал, что читаются только .json.
if entry.IsDir() || !strings.HasSuffix(entry.Name(), ".json") {
    continue
}
```

То же правило работает и для экспортируемых символов. Обязательность doc comment не означает, 
что он должен пересказывать объявление. Если конструктор, метод-обёртка или простая структура 
не скрывают контракта, символ можно оставить без комментария.

## Связное объяснение

Сравни два варианта объяснения одного и того же решения.

**Плохо (рубленые фразы, канцелярит):**
```go
// Первый Decode допускает данные после прочитанного объекта.
// Требуем EOF после него: завершающие пробелы допустимы, второй документ
// и повреждённый остаток файла должны привести к ошибке.
```

**Хорошо (одна мысль, естественные связки):**
```go
// Первый Decode читает только одно значение, поэтому вторым вызовом
// проверяем, что после него остаются лишь пробелы и конец файла.
```

Второй вариант короче, но при этом полнее передаёт причину: «почему»
проверяется EOF. Точка с запятой и рубленые предложения не нужны.

## Объяснение решения

Комментарий внутри функции нужен, когда читатель может случайно сломать
неочевидный инвариант.

```go
// Копируем набор полей родителя перед добавлением полей потомка, чтобы
// не изменить общий набор, который понадобится при сборке других потомков.
fields := maps.Clone(inherited)
```

Если просто написать «клонируем inherited», это не объяснит, **почему**
нельзя использовать исходный map. Комментарий оправдан.

## Пакеты и типы

Комментарий пакета объясняет его назначение и границы ответственности,
а не перечисляет файлы.

```go
// Package loader загружает конфигурацию из JSON-файлов и проверяет
// её обязательные поля. Содержимое вложенного поля data возвращается
// как есть — его разбирает вызывающая сторона.
package loader
```

У экспортируемого типа опиши, что представляет каждый экземпляр,
а не пересказывай поля.

```go
// ID обозначает уникальный идентификатор объекта в системе.
type ID struct {
    Group string `json:"group" validate:"required"`
    Seq   int    `json:"seq"   validate:"gte=1"`
}
```

## Формат godoc и проверка

Для ссылки на объявление используй `[Name]` или `[Type.Method]`, только
если цель действительно существует и ссылка помогает навигации.

Проверь результат через `go doc` и `gofmt`. Убедись, что комментарий
не противоречит коду и не обещает гарантий, которых нет.
