# Понятные комментарии в коде

Работай в указанной пользователем области. Не меняй поведение кода.
Запрос на комментарии не разрешает создавать README, сайт документации,
`llms.txt`, публиковать код или регистрировать проект во внешних каталогах.

## 1. Сначала реши, нужен ли комментарий вообще

Хороший комментарий — редкость. По умолчанию считай, что код в комментарии
не нуждается. Добавляй его только там, где читатель без него **точно**
споткнётся.

Прочитай код и ответь на вопрос: «Что я пойму из этого кода, если уберу
комментарий?» Если ответ «всё основное» — комментарий не нужен.

Комментарий оправдан, если объясняет:
- **Почему** сделано именно так (а не иначе).
- **Неочевидное последствие** или инвариант, который нельзя нарушить.
- **Причину** существования странного на первый взгляд условия.
- **Контракт**, который не виден из сигнатуры (формат, владение, потокобезопасность).

Комментарий **не нужен**, если он:
- Пересказывает сигнатуру или теги структуры словами.
- Повторяет имя функции или переменной.
- Объясняет очевидную конструкцию языка.
- Документирует неэкспортируемую структуру, назначение которой ясно из имён полей.

## 2. Пиши для коллеги, а не для отчёта

Представь, что объясняешь код коллеге за соседним столом. Ты не будешь
говорить «осуществляется проверка соответствия идентификатора» — ты скажешь
«функция проверяет, что ID совпадает».

**Глаголы.** Действующим лицом в doc comment обычно является само объявление
(«Parser читает», «Store хранит»). Внутри функции уместно «проверяем»,
«копируем». Избегай отглагольных существительных: не «выполняется разбор»,
а «декодер разбирает»; не «построение проверяет», а «конструктор проверяет
при сборке».

**Связность.** Сначала сформулируй мысль целиком как обычное предложение,
потом разбей на строки. Не собирай абзац из отдельных «подписей» к операциям.
Каждое следующее предложение должно развивать предыдущее (причина, следствие,
условие), а не просто добавлять ещё один факт.

**Пунктуация.** В обычном тексте не используй точку с запятой. Двоеточие
оставляй только перед явным перечислением или примером, но не как замену
союзу «потому что» или «а».

## 3. Документация Go: только необходимое

Для экспортируемых функций и методов doc comment нужен, но не любой ценой. Если всё, что ты можешь 
сказать, уже видно из имени и типов — оставь символ без комментария. Doc comment оправдан, 
если добавляет хотя бы одно из: контракт, невидимый из сигнатуры 
(формат, владение, идемпотентность, потокобезопасность); ключевые ошибки и условия их появления; 
неочевидное последствие вызова. Но это не значит, что он должен быть длинным. 
Дальше — только те условия, без которых вызывающий код ошибётся.

**Не документируй неэкспортируемые сущности**, если их роль понятна из названий
и контекста. Исключение — неочевидное поле внутри такой структуры, которое
требует пояснения (например, зачем нужен конкретный тип или почему поле изменяемо).

Для экспортируемых структур документируй поля, только если их смысл
не вытекает из имени и тега. Комментарий `// Version задаёт номер версии,
начиная с 1` рядом с тегом `validate:"gte=1"` — это шум, а не помощь.

Держи doc comment функции в пределах 2–4 строк. Если получается больше,
проверь, не пересказываешь ли ты устройство входных данных, которое уже
описано в типах.

## 4. Стиль русских комментариев

Пиши естественным русским языком.

- **Активные конструкции.** «Функция возвращает ошибку», а не «возвращается ошибка».
- **Конкретные глаголы.** «Конструктор собирает схемы», а не «осуществляется сборка схем».
- **Без канцелярита.** «Если схемы нет», а не «при отсутствии схемы».
- **Без английского порядка слов.** Не калькируй `This allows to...` в «Это позволяет...» без необходимости.
- **Связки по смыслу.** «Потому что», «поэтому», «чтобы» — только там, где они действительно выражают связь, а не для видимости плавности.

## 5. Проверь результат

Перед сдачей мысленно убери `//` и прочитай абзац целиком. Если он звучит
как набор заметок или как перевод с английского — перепиши.

Задай себе три вопроса:
1. Этот комментарий отвечает на вопрос «почему», а не «что»?
2. Без него читатель споткнётся?
3. Можно ли сказать то же самое короче, не потеряв смысл?
4. Если мысленно вставить комментарий обратно в godoc — он добавляет 
   хоть что-то к тому, что читатель уже видит в строке func ...? Если нет — удалить.

Если хотя бы на один вопрос ответ «нет» — комментарий, скорее всего, лишний.

Для Go проверь отображение через `go doc` и форматирование через `gofmt`.
