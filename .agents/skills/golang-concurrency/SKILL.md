# Конкурентность и владение

## Сначала установи протокол

Перед добавлением горутины ответь: зачем работа конкурентна, кто её запускает,
как она завершается, кто дожидается результата и куда попадает ошибка.
Оставь последовательное выполнение, если оно удовлетворяет задаче. Конкурентность
может требоваться отзывчивостью и независимостью операций, а не только скоростью.

Для каждого общего объекта установи способ доступа, для каждого канала —
отправителей, получателей, владельца закрытия и поведение при остановке.

## Выбор механизма

| Задача | Подходящий исходный вариант |
| --- | --- |
| Защита общего изменяемого состояния | Обычная map/структура и `sync.Mutex` |
| Передача работы или результата | Канал с понятным протоколом |
| Ожидание конечного набора горутин | `sync.WaitGroup` |
| Общая отмена и первая ошибка группы | `errgroup`, если он уже есть или оправдан задачей |
| Независимый счётчик с простым инвариантом | Типизированный atomic либо mutex |
| Однократная инициализация | `sync.Once`, если повтор при ошибке не нужен |

`WaitGroup` только ждёт: он не останавливает горутины и не передаёт ошибки.
Вызывай `Add` до запуска, `Done` обеспечь на выходе. Новые API используй с учётом
версии Go проекта. `sync.Map` выбирай для подходящего профиля доступа; он не
делает инварианты между несколькими ключами атомарными. `RWMutex` не быстрее
обычного mutex автоматически.

## Каналы и завершение

- Закрывает канал тот, кто может гарантировать, что отправок больше не будет.
  При нескольких отправителях это часто координатор после их завершения.
- Не закрывай канал со стороны получателя, пока отправители могут писать.
  Не каждому каналу нужно закрытие: оно должно иметь смысл для протокола.
- Указывай направление канала в API, когда оно ограничивает разрешённые операции.
- Выбирай буфер по требуемому поведению: ограниченная очередь, одноразовый результат,
  обратное давление. Нулевой буфер не является обязательным вариантом.
- Для потенциально бесконечного ожидания, которое должно отменяться, предусмотри
  `select` с `ctx.Done()` или другой гарантированный путь завершения. Не добавляй
  контекст в каждый `select` без разбора его роли.
- Если несколько веток готовы, `select` не даёт приоритета отмене. Более строгую
  гарантию прекращения приёма или запуска работ реализуй отдельным протоколом.
- Ограничивай конкурентность в точке создания работы, чтобы ожидание лимита
  само не породило неограниченное число горутин. Учитывай отмену при ожидании.

## Передача данных

Указатели допустимы в каналах при передаче владения, неизменяемых данных или
синхронизированном доступе. Копирование структуры не копирует массивы срезов,
map и объекты по указателям внутри неё. Выбери и соблюдай владение, а не заменяй
каждый указатель копией.

Не копируй mutex и содержащие его значения после начала использования.
Держи критическую секцию достаточно короткой. Если I/O нужно сериализовать,
объясни инвариант и риск блокировки; механический перенос I/O за mutex может
сломать корректность.

## Проверка

Проверь штатный выход, отмену, ошибку работника, закрытие входа и остановку при
заполненном выходе — только для существующих сценариев протокола. Используй
сигналы и ожидание событий вместо `Sleep` для порядка в тестах.
При доступной поддержке запускай затронутые тесты с `-race`; отсутствие срабатывания
не доказывает отсутствие всех гонок. `goleak` — дополнительный инструмент при
реальном риске утечек, а не обязательная зависимость любого проекта.

При ревью проверяй протокол затронутого изменения; не начинай аудит всего репозитория.
