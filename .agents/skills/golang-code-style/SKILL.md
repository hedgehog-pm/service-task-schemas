# Понятный Go-код

## Порядок работы

1. Прочитай изменяемый фрагмент вместе с вызовами и контрактом. Установи, что
   должно остаться прежним: результат, порядок действий, ошибки и изменения данных.
2. Сделай основную последовательность видимой: вход, решения, действия, результат.
3. Примени только те приёмы ниже, которые улучшают этот фрагмент. Форматирование
   доверь инструментам проекта; числовых порогов для дробления здесь нет.
4. Проверь, что упрощение сохранило область видимости, порядок вычислений и
   короткое замыкание `&&` и `||`.

## Управление потоком

- Обработай ошибки и исключительные случаи ранними выходами, когда это уменьшает
  вложенность. Не переставляй проверки с побочными эффектами без основания.
- Убери `else` после безусловного выхода, если от этого не теряется ясность.
- Предпочитай `switch`, когда связанные проверки выбирают один исход. Сравниваешь
  одно значение — `switch value`; выбираешь по условиям — `switch` без выражения.
  Независимые действия оставляй отдельными `if`.
- Дай сложному условию имя, если оно выражает понятие задачи. Не выделяй каждое
  простое сравнение в отдельный bool и не вычисляй заранее опасный вызов, который
  раньше защищало короткое замыкание.
- Держи детали рядом с их использованием. Выделение функции оценивай по смыслу,
  а не по длине; выбор API и новых типов относится к проектированию.

## Имена, API и комментарии

- Используй слова задачи и учитывай имя пакета в месте вызова. Уточняй назначение
  вместо общих `Manager`, `Helper`, `Data`, когда есть предметное имя.
- Экспортируй только используемый снаружи контракт. Группируй связанные объявления;
  не навязывай один файл на тип или фиксированный порядок всему проекту.
- Пиши комментарий о причине, ограничении, владении или неожиданном поведении.
  Не пересказывай очевидный код и не добавляй комментарий ради отступления от вкуса.
- Документируй неочевидный публичный контракт: допустимые входы, ошибки, владение,
  потокобезопасность. Полноту документации публичной библиотеки определяй задачей
  и соглашениями проекта, а не автоматическим комментарием к каждому имени.

## Объявления и значения

- Для нулевого значения уместен `var`, для сразу вычисляемого — `:=`.
  Сужай область видимости, когда это не заставляет дублировать вычисление.
- Не инициализируй каждый срез пустым литералом. `nil`-срез пригоден для `append`;
  различие `null` и `[]` учитывай на границе сериализации по контракту.
- Инициализируй map до записи. Выделяй ёмкость по известному размеру, если это
  уместно, а не по произвольному запасу.
- Используй именованные поля структурных литералов, когда это проясняет значения
  и защищает от перестановки полей. Следуй существующим соглашениям проекта.
- Применяй `range`, если индексный цикл не выражает отдельную необходимость.
  Современный синтаксис используй только при поддержке версией проекта.

## Прямое использование API

- Проследи значение до конечного использования. Промежуточное форматирование,
  копирование или преобразование оставляй, когда оно требуется контрактом,
  переиспользуется или объясняет смысл.
- Используй подходящий API для `string` или `[]byte`. Для простого преобразования
  числа подходит `strconv`, для форматирования нескольких частей — `fmt`.
  Не меняй представление данных только ради стилистического единообразия.
- Для простой конкатенации достаточно `+`; для наращивания строки в цикле рассмотри
  `strings.Builder`. Выбор обосновывай характером работы.
- Используй доступные функции `slices` и `maps`, когда они прямо решают задачу.
  Простой цикл фильтрации не требует библиотеки или отдельного generic-хелпера.


## Подробные разборы и примеры

Читай справочник по затронутой задаче, а не все файлы сразу.
Примеры включают отрицательные варианты и фрагменты с условными типами приложения.
Сохраняй их смысл и учитывай пояснения о границах применения.

- [Составные условия, короткое замыкание и выбор значения или указателя](references/details.md).
- [Переносы, объявления, литералы, ранние выходы, switch и типизация](references/core-examples.md).

Для параметров функций начни с передачи небольших значений по значению.
Указатель нужен для изменения исходного объекта, осмысленного nil или дорогого
копирования. Для методов учитывай согласованность получателей и запрет копирования
используемых mutex. Не применяй фиксированный порог размера как правило языка.

При определении функции передавай `context.Context` первым, затем входы и
при необходимости приёмники результата. Именованные результаты и короткий
`return` применяй только там, где ясно, что возвращается. Не скрывай смысл типов
через `any`, когда подходит конкретный тип или параметр типа. Reflection используй
по необходимости, а не вместо доступного типизированного API.
Побочные эффекты blank-импортов должны быть видны в месте сборки программы;
dot-импорты библиотек скрывают происхождение имён и обычно не нужны.
