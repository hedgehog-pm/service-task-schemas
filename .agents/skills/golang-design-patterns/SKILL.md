# Проектирование Go-компонентов

## Начни с нужного поведения

Установи входы, результат, инварианты и внешние эффекты операции. Прочитай
существующие места использования. Сначала предложи достаточную функцию или
конкретный тип. Если требуется выбор, коротко объясни, какую реальную проблему
решает дополнительный механизм. Не спрашивай архитектурное предпочтение заново,
если границы уже заданы проектом и задачей.

## Выбор формы

| Потребность | Исходный вариант |
| --- | --- |
| Расчёт по переданным значениям | Функция |
| Данные с совместным инвариантом или состоянием | Осмысленный тип |
| Несколько обязательных зависимостей | Явные параметры конструктора |
| Связанные настройки компонента | Структура конфигурации, если она объясняет контракт |
| Независимые необязательные настройки развивающегося публичного API | Рассмотри functional options, сравни со структурой |
| Потребителю нужен ограниченный контракт зависимости | Интерфейс на стороне потребителя |
| Передать одну операцию без собственного объекта | Параметр-функция, если это яснее интерфейса |

Количество параметров и возможное развитие API не обязывают использовать options.
Обязательные зависимости не прячь в необязательных настройках. Builder нужен
лишь при полезных этапах сборки или промежуточных состояниях.

## Интерфейсы и зависимости

- Определи, какая операция действительно нужна потребителю и зачем отделять её
  реализацию. Используй конкретный тип, пока граница не даёт понятной пользы.
- Объявляй прикладной интерфейс в пакете потребителя, с нужными ему методами.
  Одна реализация допустима: основанием может быть изоляция внешнего эффекта
  или проверка поведения потребителя. Число реализаций не является критерием.
- Не дроби связный контракт на интерфейсы по одному методу только ради размера.
  Учитывай настроенные ограничения линтера и смысл операций.
- Конструктор обычно возвращает конкретный тип. Возврат интерфейса допустим,
  если именно скрытая реализация является осмысленным публичным контрактом.
- Проверка `var _ I = (*T)(nil)` полезна, когда закрепляет нужный контракт.
  Не создавай обратный импорт реализации на потребителя ради такой проверки:
  используй место сборки или существующую компиляторную проверку присваивания.
- Именованное поле выражает внутреннюю зависимость. Встраивание типа выбирай,
  только если намеренно открываешь его методы наружу.

## Расчёт, состояние и создание

Передавай расчёту нужные значения, когда это позволяет отделить правило от I/O,
часов и сохранения. Для простого выражения не создавай отдельный слой.
Сохраняй уже осмысленный контракт в одном типе; не раскладывай его механически
на множество скаляров.

Устанавливай обязательные инварианты при создании и возвращай ошибку при
некорректной конфигурации. Полезное нулевое значение удобно, когда естественно
поддерживается типом; оно не требует ленивого подключения к БД или фиктивных
зависимостей. Если нужен конструктор, явно обозначь контракт создания.

Передавай инфраструктурные зависимости явно. Создание подключений, чтение
окружения и запуск фоновых задач не прячь в `init()`. Инициализация неизменяемой
таблицы или константного regexp на уровне пакета не равна скрытому I/O.

## Жизненный цикл и ограничения

Определи владельца ресурса: кто создаёт, использует и закрывает его, как
обрабатывается частично успешный запуск. Заимствованную зависимость не закрывай
без соответствующего контракта. Конструктор не должен незаметно запускать
неуправляемую фоновую работу.

Для внешней операции определи допустимое время и объём работы. Пригодный
дедлайн может уже приходить сверху; новый таймер на каждом слое не обязателен.
Размер очереди, число работников и способ обработки переполнения выбирай
по нагрузке и контракту, а не добавляй все механизмы на всякий случай.

Повторяй операцию лишь при понятной временной ошибке и безопасном повторе:
проверь идемпотентность, лимит попыток, общий бюджет времени и отмену ожидания.
Повтор сетевого запроса может повторить уже выполненный внешний эффект.

При остановке прекрати приём новой работы, дай текущей завершиться или отмени
её по контракту, дождись фоновых операций, затем закрой используемые ресурсы.
Конкретный протокол синхронизации выбирай по задаче конкурентности.

Нулевой элемент enum может означать Unknown, если это соответствует модели.
Статические ресурсы можно включать через `go:embed`; стабильный regexp
переиспользуй вместо компиляции на каждом вызове. `string` подходит неизменяемому
тексту, `[]byte` — изменению и I/O, `[]rune` — операциям с кодовыми точками Unicode
(кодовая точка не обязательно равна видимому символу). Не преобразуй представления
без необходимости. Для секретных токенов требуется `crypto/rand`, а не `math/rand`.
