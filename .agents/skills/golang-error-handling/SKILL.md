# Контракты ошибок

## Сначала определи обработчика

Установи, кто принимает решение об ошибке: текущая функция, вызывающий код
или внешняя граница. Проверь, должен ли потребитель различать причину, отмену,
отсутствие данных или временный сбой. Не создавай классификацию ошибок, если
по ней никто не выбирает поведение.

## Возврат и контекст

- Если текущий уровень знает полезные обстоятельства, добавь их через
  `fmt.Errorf("operation object: %w", err)`: действие, объект или этап.
- Если новой информации нет, верни `err` напрямую. Не добавляй на каждом слое
  `failed`, имя функции или повтор уже известного действия.
- Сохраняй цепочку для причин, которые вызывающий код должен распознавать.
  Используй `errors.Is` для sentinel и `errors.As` для типа в цепочке.
  Не сравнивай текст ошибки вместо её контракта.
- В сообщениях используй согласованные слова, обычно нижний регистр без конечной
  точки. Строковые значения заключай в `%q`, когда границы значения существенны.
- Не включай секреты и полные чувствительные запросы в ошибку: текст может
  попасть в лог даже без непосредственного логирования здесь.

## Форма ошибки

| Потребность вызывающего кода | Форма |
| --- | --- |
| Только сообщение о сбое | Обычная ошибка |
| Узнаваемое состояние | Sentinel уровня соответствующего контракта |
| Структурированные сведения для решения | Тип ошибки с нужными полями |
| Несколько независимых существенных причин | `errors.Join`, если поддерживается версией проекта |

Не делай обёртку-тип ради одного переименованного сообщения. Если тип хранит
причину и она входит в контракт, реализуй `Unwrap() error`.

## Граница реализации и внешнего API

Оборачивание через `%w` открывает программный доступ к причине. Реши, должна ли
деталь драйвера стать контрактом пакета. Для скрываемого состояния преобразуй
её в прикладную ошибку, например отсутствие строки — в `ErrNotFound`.
Не скрывай произвольные причины строковым `%v` автоматически на каждой границе.
При намеренном разрыве цепочки сохрани диагностическую информацию способом,
который согласован с политикой проекта и проверками линтера.

При выдаче HTTP/gRPC-ответа отдельно выбери публичный код и безопасное сообщение.
Сохранение внутренней цепочки ошибок не требует отдавать её текст клиенту.
Преобразуй известные ошибки явно; неизвестная техническая ошибка не становится
ошибкой пользовательского ввода только потому, что возникла при запросе.

## Обработка и логирование

При передаче ошибки вверх обычно не логируй её на каждом промежуточном уровне.
Логируй один раз там, где принято окончательное решение о сбое. Если операция
подавляет ошибку и продолжает работу, текущий уровень может быть её обработчиком.
Отмена клиентом не обязательно является аварией: выбери уровень по последствиям.

Используй принятый в проекте `slog`. При доступном контексте передавай его.
Сообщение события оставляй постоянным, идентификаторы и причину передавай полями:

```go
slog.ErrorContext(ctx, "save attachment failed",
	"attachment_id", attachment.ID,
	slog.Any("error", err),
)
```

Ошибка может содержать полезный объект операции; постоянным должен оставаться
текст события, используемый для группировки. Не добавляй специальную библиотеку
ошибок ради самого наличия error handling.

## Panic и освобождение ресурсов

Ожидаемые ошибки ввода, сети и файлов возвращай как `error`. Panic не заменяет
обычный путь ошибки. `recover` используй в обоснованной границе изоляции, если
после нарушения действительно безопасно продолжать; не превращай panic в успех.
`recover` в одной горутине не перехватывает panic другой.

У ошибок записи, закрытия и фоновых операций должен быть наблюдаемый обработчик.
Не отбрасывай их механически; значимость ошибки оценивай по контракту ресурса.
