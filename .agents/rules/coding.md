# Понятный Go-код

Применяй эти правила при написании, изменении и ревью Go-кода.
Цель — чтобы читатель мог восстановить логику с небольшим количеством переходов и предположений.
Оформление и механические соглашения определяет конфигурация линтеров проекта.

## Делай ход выполнения видимым

Располагай код так, чтобы сверху вниз читались входные данные, решения, действия и результат.
Основную последовательность действий держи рядом; подробности выноси, когда они мешают увидеть эту последовательность.
Из названия вызова должно быть понятно, какой шаг он выполняет и меняет ли состояние.

## Выражай взаимоисключающие исходы одним ветвлением

Когда несколько проверок выбирают один из исходов одной операции, предпочитай `switch` цепочке связанных `if`, если так варианты читаются яснее. Для условий используй `switch` без выражения, для сравнения одного значения — `switch` по этому значению.
Сохраняй порядок проверок, ранние выходы и обработку остальных случаев. Независимые действия, которые могут выполняться вместе, оставляй отдельными `if`: `switch` выполняет только первую подходящую ветку.

## Выделяй части по смыслу

У функции, типа и пакета должна быть понятная обязанность, которую можно назвать словами задачи.
Выделяй отдельную часть, когда она скрывает существенную подробность, выражает самостоятельное правило или позволяет повторно использовать связанную логику.
Сокращение числа строк и прохождение проверки сложности сами по себе не объясняют новое разделение.
Пара простых действий часто понятнее на месте, чем за дополнительными вызовами и мелкими типами.

## Выбирай простое достаточное решение

Сначала проверь существующий код, стандартную библиотеку и уже используемые зависимости.
Добавляй механизм под конкретную потребность задачи; каждое дополнительное состояние, ветвление и уровень косвенности увеличивает объём того, что читатель должен удерживать в голове.
Если общий случай уже входит в требования, вырази его целиком. Возможности на предполагаемое будущее добавляй, когда появится задача.

Определяй интерфейсы на стороне использования, в пакете потребителя, и включай только методы, которые ему нужны.
Не объявляй интерфейс рядом с реализацией или заранее ради возможной замены зависимости.
Пока у потребителя нет реальной потребности в интерфейсе, используй конкретный тип или передавай готовые данные.
Количество реализаций само по себе не определяет, нужен ли интерфейс.

## Отделяй расчёт от управления операцией

Когда расчёт можно выразить через входные значения, передавай ему эти значения.
Чтение внешних данных, получение текущего времени, сохранение результата и управление последовательностью оставляй у кода, выполняющего операцию.
Выделение полезно, если позволяет понять и проверить правило независимо от окружения.
Для простого выражения достаточно локального кода; отдельный тип или функция нужны, когда это улучшает понимание.

## Делай зависимости и изменения состояния явными

Передавай данные и зависимости, которые нужны для выполнения работы.
Сохраняй связанные данные в осмысленном типе, если он уже выражает используемый контракт; не раскладывай его механически на множество параметров.
Не передавай целый сервис или конфигурацию только ради доступа к одному значению.

По коду должно быть понятно, кто создаёт данные, кто вправе их менять и сколько они живут.
Неожиданные изменения переданных указателей, срезов и map усложняют понимание вызывающего кода.
Для фоновой работы должно быть понятно, кто её завершает и как наблюдается завершение.

## Пиши на языке задачи и сохраняй небольшой API

Используй одинаковые слова для одинаковых понятий во всём проекте.
Имена должны объяснять назначение и существенные различия; выбирай конкретное действие или понятие вместо общего обозначения вроде `Manager`, `Helper` или `Data`.
Учитывай имя пакета: выражение в месте вызова должно читаться естественно.
Экспортируй то, что нужно пользователям пакета, сохраняя детали реализации внутри.

## Добавляй информацию на своём уровне

При передаче ошибки добавляй полезные обстоятельства, известные текущему коду: операцию, объект или этап.
Если дополнительного контекста нет, возвращай ошибку напрямую.
Сохраняй сведения, по которым вызывающий код принимает решение об обработке ошибки.

Имена объясняют назначение. Комментарии объясняют неочевидное поведение, причины и ограничения.
Размещай объяснение рядом с кодом, которому принадлежит описываемый контракт или инвариант.
Используй конкретные термины проекта и короткие предложения.

## Сохраняй смысл и согласованность

Перед изменением прочитай затрагиваемый код, его вызовы и существующие решения похожих задач.
Используй принятые в проекте понятия и подходы. Отступление должно решать конкретную проблему; случайное соседство само по себе не делает старое решение образцом.
Не меняй наблюдаемое поведение ради более короткой записи или симметричной структуры.
При замене пути выполнения сохрани его проверки, побочные эффекты и гарантии, если задача явно не меняет их.

При выборе между решениями сначала сохраняй корректность и контракт, затем ясность чтения; краткость оценивай после них.

## Убирай промежуточную работу, которую позволяет избежать уже выбранный API. 

Прослеживай путь данных до конечного использования: форматирование, преобразование или копирование должно иметь понятную причину. Предпочитай непосредственную операцию, если она столь же понятна и сохраняет поведение. Учитывай порядок вычислений, побочные эффекты и обработку ошибок. Промежуточное значение оправдано, когда объясняет смысл, переиспользуется или требуется контрактом API.

## Небольшие примеры

Примеры ниже показывают решения в отдельных ситуациях. Переноси в задачу причину выбора, а размер функций и состав типов определяй по её коду.

### Расчёт срока подписки

У действующей подписки новый период начинается с текущего срока окончания, у истёкшей — с момента продления.
Расчёт получает нужные значения и не обращается к часам или хранилищу:

```go
func extendedExpiry(expiresAt, now time.Time, period time.Duration) time.Time {
	base := expiresAt
	if base.Before(now) {
		base = now
	}
	return base.Add(period)
}
```

Выполняющий операцию код получает время и сохраняет результат.
Проверка допустимости периода и права на продление относятся к контракту операции; этот фрагмент показывает только расчёт:

```go
now := time.Now()
expiresAt := extendedExpiry(subscription.ExpiresAt, now, period)
if err := store.SetExpiry(ctx, subscription.ID, expiresAt); err != nil {
	return fmt.Errorf("extend subscription %s: %w", subscription.ID, err)
}
```

Разделение позволяет отдельно проверить правило продления и понять, где меняется состояние.
Для такого расчёта достаточно функции; отдельная иерархия политик не добавляет нужного поведения.

### Последовательность действий и лишнее дробление

Если завершение задачи состоит из присвоения статуса и сохранения, эти действия читаются непосредственно.
Здесь `task` — принадлежащая текущей операции копия данных; при ошибке сохранения эта копия больше не используется:

```go
task.Status = StatusCompleted
if err := store.Save(ctx, task); err != nil {
	return fmt.Errorf("complete task %s: %w", task.ID, err)
}
```

В этой ситуации пара вызовов `prepareCompletion(task)` и `persistCompletion(ctx, task)` скрыла бы простые действия.
Если завершение включает переходы состояний и бизнес-ограничения, выделение `Complete` может выразить настоящий контракт.
Основание для выделения — смысл операции и её сложность.

### Контекст ошибки

При обработке нескольких вложений вызывающий код знает, какое из них не удалось сохранить:

```go
return fmt.Errorf("save attachment %s: %w", attachment.ID, err)
```

Хранилище сообщает техническую причину, этот уровень добавляет объект операции.
Обёртка с текстом `save failed` полезной информации здесь не добавляет.

## Перед завершением изменения

Просмотри изменённый код как читатель: виден ли ход выполнения, понятны ли обязанности частей, зависимости и изменения состояния?
Удали введённые тобой промежуточные сущности, которые не помогают ответить на эти вопросы.
Проверь изменённое поведение подходящими для задачи проверками и выполни проверки проекта.
